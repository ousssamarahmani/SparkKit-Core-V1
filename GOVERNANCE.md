# SparkKit Governance

SparkKit is currently maintained under a benevolent-maintainer model while the
version 0.1 foundation is established. This document will evolve as repeat
contributors take on sustained project responsibilities.

## Decision making

- Small, reversible implementation decisions are made through pull-request review.
- Changes to product scope, package boundaries, security guarantees, compatibility,
  or public APIs require an architecture decision record in `docs/adr`.
- Maintainers prefer documented tradeoffs and working evidence over vote counting.
- Planned features must not be represented as implemented capabilities.

## Maintainer responsibilities

Maintainers are responsible for:

- protecting the security and portability principles in `ARCHITECTURE.md`;
- reviewing contributions consistently and respectfully;
- keeping the public roadmap aligned with verified implementation;
- documenting breaking changes and release decisions;
- recognizing contributors in release notes; and
- applying the Code of Conduct.

## Becoming a maintainer

Maintainer access is earned through sustained, constructive contributions and
sound judgment across code review, documentation, issue triage, or community
support. There is no contribution-count threshold. Existing maintainers invite
new maintainers after reviewing the person's work over time.

## Project changes

This governance model may be revised through a public proposal when the project
has enough active maintainers and contributors to benefit from broader shared
ownership.
